# 代码审查要点

## 类型安全

### TypeScript
- ✅ 所有函数都有明确的类型定义
- ✅ 组件 Props 使用接口定义
- ✅ 避免使用 `any` 类型
- ✅ API 响应类型与后端 Schema 一致

### Python
- ✅ 所有函数都有类型提示
- ✅ 使用 Pydantic Schema 进行数据验证
- ✅ 数据库模型使用 SQLAlchemy 类型注解

### Dart
- ✅ 所有变量和函数都有明确的类型
- ✅ 使用 `freezed` 和 `json_serializable` 生成类型安全的模型

## 错误处理

- ✅ 所有 API 调用都有错误处理
- ✅ 异步操作都有 try-catch 或错误回调
- ✅ 错误信息对用户友好
- ✅ 关键错误记录日志

## 代码质量

### 可读性
- ✅ 函数和变量命名清晰
- ✅ 代码有适当的注释
- ✅ 复杂逻辑有解释说明

### 可维护性
- ✅ 遵循单一职责原则
- ✅ 代码结构清晰，目录组织合理
- ✅ 避免重复代码（DRY 原则）

### 性能
- ✅ 数据库查询优化（避免 N+1 查询）
- ✅ 前端组件使用 memo 优化
- ✅ 图片和资源使用缓存
- ✅ 代码分割和懒加载

## 安全性

- ✅ 所有 API 端点有适当的认证和授权
- ✅ 用户输入都经过验证和清理
- ✅ 敏感信息不暴露在日志中
- ✅ 使用环境变量管理配置

## 一致性

### 前后端一致性
- ✅ API 接口定义一致
- ✅ 数据模型保持一致
- ✅ 错误响应格式一致

### 跨平台一致性
- ✅ 移动端与 Web 端功能一致
- ✅ 用户体验保持一致（移动端使用 Material Design 适配）
- ✅ 业务逻辑保持一致（移动端参考 student-web 的实现）
- ✅ API 接口一致（使用相同的 endpoints）
- ✅ 数据模型保持一致（确保 API 响应结构一致）

## 测试

- ✅ 关键功能有测试覆盖
- ✅ 边界情况有测试
- ✅ 错误情况有测试

## 文档

- ✅ 复杂功能有文档说明
- ✅ API 接口有注释说明
- ✅ 配置项有说明文档

## 代码风格

- ✅ 遵循项目的代码风格规范
- ✅ 使用项目统一的格式化工具
- ✅ 导入顺序符合规范
- ✅ 命名符合规范

## 架构遵循

- ✅ 遵循项目的分层架构（路由层 → 服务层 → 数据层）
- ✅ 遵循项目的目录结构（页面结构、组件组织等）
- ✅ 遵循项目的状态管理模式（unstated-next + ahooks / Riverpod）
- ✅ 遵循项目的路由规范（react-router-dom / GoRouter）
- ✅ 遵循 SQLAlchemy 2.0 ORM 风格（后端）
- ✅ 遵循代码生成规范（Flutter 模型修改后必须运行 `./build.sh`）
